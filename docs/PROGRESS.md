## 时间线

### 2026-10-25 · 环境与模型

- 选定技术路线：放弃官方 PyTorch（需 Linux + 7.7 GiB 显存），改用 `Breeze-TTS-2.cpp`（GGUF + Vulkan）
- 量化档位实测选型：Q8_0（3.3 GB，峰值 4.2 GB 显存），F16 在 8GB 卡上必爆
- 跑通中文合成，实测 1.25× 实时
- 解决国内网络：`hf-mirror.com` 下权重、`gh-proxy.com` 下二进制

### 2026-10-26 · 从 TTS 到 QQ 机器人

**上午 · 接入**
- 调研两条路线：社区 `qq-bridge` + DSH，与自写 MCP
- 结论：WorkBuddy 本身就是 agent，不需要 DSH；且 qq-bridge 的语音只能播库存，没有 TTS
- 自写 `qq_mcp`（MCP stdio 服务器，纯标准库），6 个工具
- 打通发送：`qq_send_voice` → `tts.py` → `record` 段 → QQ 语音条

**下午 · 能力扩展**
- 音色批量试听：萝莉 320Hz / 少女 273 / 年轻女孩 250 / 御姐 192~224（基频中位数）
- 多角色配音：`dub_dialog.py`，逐句合成 + 拼接
- 音色一致性修正：发现逐句换 `instruction` 会导致「不是同一个人」，改用 `--save-voice` 克隆锁定音色
- 新增人设 `persona.json`、记忆库 `memory.py`、上下文工具 `qq_context`

**傍晚 · 工程化**
- 架构设计收敛为 `docs/ARCHITECTURE.md`
- 补齐 LICENSE（MIT）、NOTICE（第三方与商用限制）、README（产品介绍）
- 一键启动 `start.py` + `启动.bat`，7 项预检实测通过
- 发布到 GitHub：<https://github.com/Z-rocks/breeze-qq-bot>

### 2026-10-26 晚 · v0.2.0 生产就绪

- `guard.py`：白名单 + 急停 + 频率，默认拒绝
- `privacy.py`：入站脱敏（占位符）+ 出站审查（拦路径/密钥/代码块/URL）

## 已知问题

| 问题 | 影响 | 临时方案 |
| --- | --- | --- |
| NapCat 不能由外部进程托管 | 被沙盒回收即掉线 | 用 `start.py` 常驻，或手动双击启动 |
| 8GB 显存只能单实例 | 并发请求 OOM | 串行发送，勿同时多条 |
| 合成 1.25× 实时 | 30 秒语音要等 24 秒 | 发送前给「正在输入」提示 |
| 单次生成上限 60 秒 | 长文需切段 | `--split-chars` 控制 |
| 快速登录偶发失效 | 需重新扫码 | 强杀进程后必然触发，尽量正常退出 |
| 模型权重非商用 | 整体不可商用 | 商用走 BreezeBlue 官方平台 |

## 技术决策记录

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 推理实现 | Breeze-TTS-2.cpp 而非官方 PyTorch | 8GB 显存 + Windows，官方要 Linux + 7.7 GiB |
| 量化 | Q8_0 | 无可闻损失，显存 4.2 GB 留足余量 |
| agent 宿主 | WorkBuddy 而非 DSH | 本身就是 agent，少一层进程 |
| 协议接入 | NapCat + OneBot 11 | 生态最成熟，语音自动转 SILK |
| 记忆存储 | SQLite | 零依赖，单文件，够用 |
| 检索 | 2-gram + OR + 命中排序 | 不装分词库也能搜中文 |
| 音色一致性 | 克隆锁定而非逐句描述 | 逐句改指令会变成不同的人 |
| 许可 | 代码 MIT + 权重非商用 | 权重许可限制无法绕过，如实声明 |
